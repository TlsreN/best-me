# 02 技术路线与限制

## 一、三条硬事实

1. **原生 iOS 必须用 Mac 编译。** Xcode 只跑在 macOS 上，iPhone / iPad 不能编译原生 App。
2. **HealthKit 只有原生 App 能读。** 网页（含添加到主屏幕的 PWA）没有任何途径直接访问「健康」数据。
3. **iPad 上的 Swift Playgrounds 能跑 SwiftUI**，但不支持 HealthKit，也不能直接上传 App Store。

结论：**没有 Mac 就拿不到原生 + HealthKit 的组合。** 这不影响先把记录和可视化做出来。

## 二、两条路线

| | A. PWA（网页应用） | B. 云 Mac + SwiftUI 原生 |
| --- | --- | --- |
| 现在能不能做 | 能，今天就能用 | 不能，需先租云 Mac |
| 成本 | 0 | 约 30–100 元/月（MacinCloud / MacStadium） |
| 装到 iPad | Safari 打开 → 分享 → 添加到主屏幕，全屏无地址栏 | 需编译安装，免费证书 7 天重签 |
| 离线可用 | 是（Service Worker + IndexedDB） | 是 |
| Apple 健康 | 不能直连，走「快捷指令」导出导入 | 可直连，自动同步 |
| Apple Watch | 只能间接（经由健康导出） | 可做手表 App |
| 上架 App Store | 不能 | 能 |
| 迭代速度 | 改完刷新即生效 | 每次远程编译，慢 |

## 三、建议：先 A，后 B

**理由**：这类记录工具真正会死掉的原因不是功能不够，而是「第三天就不想记了」。先用 PWA 把记录闭环跑通 2–4 周，验证自己的使用习惯，再决定要不要花钱上原生。

- **v0.x（现在）**：PWA，iPad 优先布局，iPhone 自适应
- **v0.5**：数据层与规则层稳定，导出格式固定
- **v1.0**：拿到 Mac（自购/借用/云 Mac）后，用 SwiftUI 重写外壳，复用同一套数据模型与规则，接入 HealthKit

## 四、健康数据桥接（PWA 阶段）

iOS「快捷指令」可以读取健康样本并写文件：

```
快捷指令：查找健康样本（体重 / 活动能量 / 运动时长 / 步数 / 心率）
   → 格式化为 CSV → 存到「iCloud 云盘/健康导出/」
App 内「导入健康数据」按钮 → 选择该 CSV → 合并进当天记录
```

- 可设自动化：每天 23:00 自动跑一次，你什么都不用点
- 你另一个健身 App 的数据：**只要它把训练写入「健康」，就会一并被读到**
- 需要你告诉我它是哪个 App（Keep / 训记 / Strong / 其他），我确认它是否真的写健康

## 五、为「以后上架」预留的三件事

1. **数据模型用 JSON Schema 定义**，`docs/01` 里的实体直接落成 schema，PWA 与未来的 SwiftUI 共用
2. **导出格式固定**：`full-backup.json`（全量）+ `day.csv` / `week.csv`（可读），格式一旦定版不再改
3. **业务逻辑与界面分层**：热量与宏量计算、调整规则写成纯函数模块，界面只做展示

## 六、已知代价（先接受，后解决）

- PWA 存的是浏览器存储，长期不用有被系统清理的风险 → 每周首次打开时提醒导出备份，且每次记录立即写入
- 通知能力弱于原生（喝水/记录提醒可能不准时）
- 没有 HealthKit 的后台自动同步，靠快捷指令定时跑
